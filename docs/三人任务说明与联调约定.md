## 0. 一页总览

| 角色 | 一句话职责 | 主要目录 | 第一个交付（D3） |
|---|---|---|---|
| **A 前端** | 把事件流画成会商页面，以及总览、触发规则等配套页面 | `web/` | 用样本回放跑出会商页（已完成） |
| **B 后端** | 运行服务（事件推送、协作中枢、回放）+ Agent 编排（把会商原型拆成正式模块） | `server/` | 回放模式的 SSE 服务（联调 1） |
| **C 业务与接入** | 调研真实的盾构业务逻辑，整理成业务知识包，并确定接到系统哪里 | `docs/业务知识/` | 差异清单：现有 Demo 设定里哪些和真实业务不符 |

> 10/13 调整分工：原 C（Agent 编排）的工作并入 B，因为会商原型已基本成型，剩下的主要是拆分迁移，由一个人写可以省掉 B、C 之间的联调。新的 C 负责业务真实性。

**联调分三步走，每一步只引入一个新变量：**

```
联调 1（D3）  A 前端  ←SSE─  B 后端（回放模式，不调模型）
             验证：A 和 B 之间的接口、SSE、断线重连

联调 2（D5）  A 前端  ←SSE─  B 后端（运行服务 + 编排，真实调用模型）
             验证：正式后端的真实运行能完整显示

联调 3（D7）  A 前端  ─REST→  B 后端
             验证：现场回答、人工审核、刷新恢复、预检

业务接入（D8）C 的业务知识包  →  B 的场景数据和提示词  →  批量运行，C 评判结论
```

回放模式是联调的关键：B 在服务端把 `web/dev/sample-run.jsonl` 按原始时间间隔通过真实的 SSE 推出去。这样 A 和 B 可以在编排拆完之前就把整条链路调通；之后接入编排时，如果出了问题，就可以确定是编排的问题。

## 2. A 前端

### 2.1 目标

按设计文档第 3 节做出会商页及配套页面。重点是让没参与项目的人一眼看出 Agent 之间在交流、质疑、改口，以及最终结论是什么。

### 2.2 技术栈

React 19 + Vite + TypeScript + Tailwind v4 + `motion` + Recharts + `lucide-react` 图标；协作网络用 `@xyflow/react`；详情抽屉用 `react-markdown`。浅色企业后台风格、系统字体。`web/` 已加入根目录 `package.json` 的 workspaces，依赖 `@tbm/shared`。

### 2.3 数据层：一个接口，两种实现

UI 组件不允许直接碰 `EventSource` 或 `fetch`，统一走下面的接口，这样回放和真实运行可以随时切换：

```ts
// web/src/data/source.ts
import type { RunEvent, Evidence, RingPoint, CreateRunRequest } from '@tbm/shared'

export interface RunSource {
  createRun(req: CreateRunRequest): Promise<string>                       // 返回 runId
  subscribe(runId: string, onEvent: (e: RunEvent) => void, after?: number): () => void
  evidence(runId: string, id: string): Promise<Evidence>
  rings(from: number, to: number): Promise<RingPoint[]>
  answer(runId: string, questionId: string, text: string): Promise<void>
  review(runId: string, version: number, decision: 'approve' | 'reject', comment?: string): Promise<void>
  abort(runId: string): Promise<void>
  health(): Promise<HealthResponse>                                       // 开始页预检
}
```

| 实现 | 用途 | 数据来源 |
|---|---|---|
| `LocalReplaySource` | D1–D3 独立开发；不需要后端 | `web/dev/sample-run.jsonl`、`sample-evidence.json`、`sample-rings.json`；按事件时间戳间隔播放，支持倍速；`answer`、`review` 只在控制台打印 |
| `HttpSource` | 联调和演示 | 按 `api.ts` 调后端；`subscribe` 用 `EventSource('/api/runs/:id/events')` |

通过环境变量切换：`VITE_SOURCE=local`（默认）或 `VITE_SOURCE=http`。

**SSE 处理要求**：

- 每个事件带 `seq`，reducer 只接受 `seq` 比当前大的事件，重复的直接丢弃（断线重连时服务端会补发，可能有重叠）。
- 浏览器的 `EventSource` 断线后会自动重连并带上 `Last-Event-ID`，不需要手动处理。
- 收到 `run.finished` 后主动 `close()`，否则浏览器会一直重连。

### 2.4 状态：一个 reducer

```ts
// web/src/state/reducer.ts
reduce(state: ViewState, event: RunEvent): ViewState
```

`ViewState` 至少包含：

| 字段 | 来自哪些事件 | 用在哪里 |
|---|---|---|
| 运行信息、触发方式、当前阶段、计时 | `run.started`、`stage.changed`、`run.finished` | 会商页页头、步骤条 |
| 快照（环号、缺失项） | `snapshot.created` | 目前页面未展示（可用于说明"缺哪些数据"） |
| 每个 Agent 的状态、最新一行思考、token | `agent.status`、`agent.delta`、`usage.updated` | 协作网络节点、Agent 配置页 |
| 每个 Agent 的完整思考和工具调用 | `agent.delta`、`tool.started`、`tool.finished` | 节点详情抽屉 |
| 连线：两两之间的消息数、最近一条消息 | `peer.message` | 协作网络连线、会商记录 |
| 协作板：判断、修正历史、挂在下面的反应 | `finding.posted`、`finding.revised`、`peer.message`（带 `findingId` 的） | 立场矩阵 |
| 现场提问（待回答 / 已回答） | `human.asked`、`human.answered` | 现场回答卡片 |
| 会商 | `session.opened`、`session.closed` | 立场矩阵展开行、会商记录 |
| 结论、会签、审核 | `conclusion.drafted`、`signoff.submitted`、`review.decided` | 结论横幅、立场矩阵"写入结论"列、审核栏 |
| 协作计数 | `collab.stats` | 协作网络视图的计数器 |

reducer 必须是纯函数：快进回放（设计文档高光 ⑥）就是把同一份事件列表加速重新喂一遍。

## 3. B 后端（一）：运行服务

### 3.1 目标

一个稳定的运行服务：管理运行生命周期，把事件可靠地推给前端（断线能补发），实现协作中枢，并支持回放模式。B 同时负责第 4 节的 Agent 编排，两部分合并排期见 3.6。

可对照 `server/spike/live-bridge.ts`：它为了让前端提前接上真实会商，已按 `api.ts` 实现了 live 模式下的创建、状态、SSE 补发、证据、`/answer` 和 `/review` 的 404 / 409 校验、中止。它不是正式实现：没有回放模式、只能同时跑一场、不落盘、`/health` 不调模型、没有 CollabHub（协作逻辑全在 `debate.ts` 里）。正式后端上线后删除。

### 3.2 技术栈

Node 22 + TypeScript，用 `tsx` 运行。路由建议用 Hono（`@hono/node-server`），自带 SSE 支持；也可以用原生 `node:http`，只要对外行为符合 `api.ts`。

### 3.3 模块

| 模块 | 职责 | 要点 |
|---|---|---|
| `bus/EventBus` | 每个运行一份事件日志 | **入库时深拷贝 payload**（`structuredClone`），否则之后修改对象（如修正判断）会把已发出的事件一起改掉，`validateRun()` 的版本号检查会报出来；分配 `seq`（从 1 开始连续）和 `ts`；`agent.delta` 按 Agent + kind 每 50 ms 合并；写 `server/runs/<runId>.jsonl`；支持订阅和"从某个 seq 之后补发" |
| `collab/Hub` | 实现 `CollabHub` 接口 | 编号规则 E/H/F/M/Q/S 各自从 1 递增；每个方法发出的事件见接口注释；统计规则见 3.4 |
| `run/RunManager` | 运行生命周期 | 同一时间只允许一个运行（否则 409）；发 `run.started`、`snapshot.created`；调用编排（第 4 节）；编排结束后切到 approval 并等待审核；审核后切到 closed，发 `run.finished`；编排抛错时发 `run.finished(failed)` |
| `run/replay` | 回放模式 | 读 `web/dev/sample-run.jsonl`，按原始时间间隔（除以倍速）重新发出，`runId` 和 `seq` 换成本次运行的；遇到 `human.asked` 时**暂停，等待 `/answer`**；到 approval 阶段时**等待 `/review`**，这样 A 可以在回放模式下调现场回答和审核 |
| `http/routes` | REST + SSE | 严格按 `api.ts`：路径、状态码、`{ error }` 错误格式、SSE 帧格式、15 秒心跳、`Last-Event-ID` 和 `?after=` 两种补发方式 |
| `health` | 预检 | 调一次模型（一句话、不带工具），返回首 token 延迟；失败返回 503 |

### 3.4 CollabHub 统计规则

前端顶栏直接显示这些数字，所以规则要固定：

| 字段 | 规则 |
|---|---|
| `peerMessages` | `send()` 时 `from` 和 `to` 都是专业 Agent（地质、掘进、刀盘、渣土）的消息条数 |
| `asks` / `challenges` / `endorses` | `send()` 时 kind 分别为 ask / challenge / endorse 的条数 |
| `revisions` | `reviseFinding()` 次数 |
| `crossCitations` | `send()` 的 `refs`、`postFinding()` 的 `evidence`、`reviseFinding()` 的 `cites` 中，属于其他 Agent（含现场）的编号个数 |
| `humanAsks` | `askHuman()` 次数 |
| `signoffs` | `signOff()` 次数 |

### 3.5 不调模型的自测（可选）

### 3.7 自测命令（写成脚本）

```bash
# 开一个回放运行，倍速 10
curl -s -XPOST localhost:8787/api/runs -H 'content-type: application/json' -d '{"mode":"replay","speed":10}'
# → {"runId":"..."}

# 真实运行，自定义问题并带触发来源（question 仅 live 生效；trigger 原样出现在 run.started）
curl -s -XPOST localhost:8787/api/runs -H 'content-type: application/json' \
  -d '{"mode":"live","question":"525 环后扭矩为何持续偏高？","trigger":{"kind":"manual","id":"manual","name":"人工发起","reason":"夜班反馈扭矩偏高"}}'

# 订阅事件流
curl -N localhost:8787/api/runs/<runId>/events

# 断线补发：只要 seq > 100 的
curl -N 'localhost:8787/api/runs/<runId>/events?after=100'

# 回答现场提问、审核
curl -XPOST localhost:8787/api/runs/<runId>/answer -H 'content-type: application/json' -d '{"questionId":"Q1","text":"有，出土偏干"}'
curl -XPOST localhost:8787/api/runs/<runId>/review -H 'content-type: application/json' -d '{"version":1,"decision":"approve"}'
```

## 5. C 业务与接入

### 5.1 目标

Demo 里的场景数据、异常阈值和专家的判断思路，目前都是团队自己推算的（设计文档 5.1 节："团队里没有盾构专业背景"）。C 负责找到真实的盾构施工业务逻辑，整理成能直接落到系统里的"业务知识包"，并确定每一项接到哪里。目的有两个：

1. 演示时经得起甲方专业人员追问，结论和建议符合行业常识。
2. 为后续接入甲方真实数据做准备：甲方《框架设计说明书》列出了"需要甲方确认的事项"（数据接口、指标口径、算法与专业规则、业务评估案例），C 的调研结果就是我们这边的答卷和提问清单。

C 不需要写代码，但交付物要按 5.4 的模板填，B 和 A 才能直接接入。

### 5.2 调研什么

先聚焦 Demo 的场景"掘进效率异常诊断"，有余力再扩展到扭矩异常、结泥饼、喷涌、刀具异常磨损等问题。

| 主题 | 要回答的问题 | 接到哪里 |
|---|---|---|
| 指标口径 | 推进速度、贯入度、刀盘扭矩、总推力、转速、土仓压力、出土量、泡沫注入率 FIR、发泡倍率 FER、原液流量、坍落度、刀具磨损、地层分类和卵石含量：含义、单位、6 m 级土压平衡盾构的常见量级、正常范围、报警阈值 | 场景数据 `server/src/data/scenario.ts`；数据工具的说明文字；触发规则默认阈值 `web/src/data/triggers.ts` |
| 诊断逻辑 | 对每类异常：可能的原因有哪些，各原因看哪些数据、有什么特征（量级、时间先后、联动关系），怎样排除 | 各专家提示词中的专业知识段落；参考答案 |
| 专业分工 | 现实中地质、掘进、刀盘、渣土各岗位看什么数据、负责判断什么；有没有缺的角色（如盾构司机、设备、测量） | `agents.ts` 的数据域；提示词中的角色说明 |
| 处置措施 | 每个原因对应的常规措施和适用条件（如调整泡沫参数、开仓检查、换刀） | 评判结论中"建议措施"的标准（平台只给建议，不控制设备） |
| 现场信息 | 哪些信息只有现场人员知道、通常怎么问、怎么回答 | 现场话术卡（设计文档 2.5）；快照缺失项 |
| 数据来源 | 真实项目中这些数据来自什么系统（PLC/SCADA、泡沫系统、地勘报告、刀具检查记录、渣土试验），字段、采样频率、时间口径 | 将来接入真实数据的连接器；向甲方要资料的清单 |

### 5.3 资料来源与要求

- 优先使用国家和行业规范（如 GB 50446《盾构法隧道施工及验收规范》）、教材、设备厂商手册、公开的工程案例和论文；能向甲方或熟人工程师确认的更好。
- **每个数值、每条规则都要标出处**。查不到就写"未找到依据"，不要凭感觉补；不同来源有矛盾时都列出来。
- 数值写清楚适用条件（盾构类型、直径、地层），不要把某个项目的个案当成通用标准。
