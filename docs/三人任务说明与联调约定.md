## 0. 一页总览

| 角色 | 一句话职责 | 主要目录 | 第一个交付（D3） |
|---|---|---|---|
| **A 前端** | 把事件流画成"圆桌会商指挥舱" | `web/` | 用样本回放跑出圆桌画布和协作板 |
| **B 后端** | 运行管理、事件推送、协作中枢 | `server/src/`（除 `agents/`、`tools/`、`orchestration/`） | CollabHub 实现 + 回放模式的 SSE 服务 |
| **C Agent** | 让 5 个 Agent 真实会商 | `server/src/agents/`、`tools/`、`orchestration/` | 原型拆成正式模块，接上 B 的 CollabHub |

**联调分三步走，每一步只引入一个新变量：**

```
联调 1（D3）  A 前端  ←SSE─  B 后端（回放模式，不调模型）
             验证：A 和 B 之间的接口、SSE、断线重连

联调 2（D5）  A 前端  ←SSE─  B 后端  ←─  C 编排（真实调用模型）
             验证：B 和 C 之间的接口；真实运行能完整显示

联调 3（D7）  A 前端  ─REST→  B 后端  →  C 编排
             验证：现场回答、人工审核、刷新恢复、预检
```

回放模式是联调的关键：B 在服务端把 `web/dev/sample-run.jsonl` 按原始时间间隔通过真实的 SSE 推出去。这样 A 和 B 可以在 C 完成之前就把整条链路调通；之后接入 C 时，如果出了问题，就可以确定是 B 和 C 之间的问题。

## 2. A 前端

### 2.1 目标

按设计文档第 3 节做出圆桌会商指挥舱。重点是让没参与项目的人一眼看出 Agent 之间在交流、质疑、改口。

### 2.2 技术栈

React 19 + Vite + TypeScript + Tailwind v4 + shadcn/ui + `@xyflow/react` 12 + `motion` + Recharts。在 `web/` 下初始化，加入根目录 `package.json` 的 workspaces，依赖 `@tbm/shared`。

### 2.3 数据层：一个接口，两种实现

UI 组件不允许直接碰 `EventSource` 或 `fetch`，统一走下面的接口，这样回放和真实运行可以随时切换：

```ts
// web/src/data/source.ts
import type { RunEvent, Evidence, RingPoint, CreateRunRequest } from '@tbm/shared'

export interface RunSource {
  createRun(req: CreateRunRequest): Promise<string>                       // 返回 runId
  subscribe(runId: string, onEvent: (e: RunEvent) => void, after?: number): () => void
  evidence(runId: string, id: string): Promise<Evidence>
  rings(from: number, to: number): Promise<RingPoint[]>
  answer(runId: string, questionId: string, text: string): Promise<void>
  review(runId: string, version: number, decision: 'approve' | 'reject', comment?: string): Promise<void>
}
```

| 实现 | 用途 | 数据来源 |
|---|---|---|
| `LocalReplaySource` | D1–D3 独立开发；不需要后端 | `web/dev/sample-run.jsonl`、`sample-evidence.json`、`sample-rings.json`；按事件时间戳间隔播放，支持倍速；`answer`、`review` 只在控制台打印 |
| `HttpSource` | 联调和演示 | 按 `api.ts` 调后端；`subscribe` 用 `EventSource('/api/runs/:id/events')` |

通过环境变量切换：`VITE_SOURCE=local`（默认）或 `VITE_SOURCE=http`。

**SSE 处理要求**：

- 每个事件带 `seq`，reducer 只接受 `seq` 比当前大的事件，重复的直接丢弃（断线重连时服务端会补发，可能有重叠）。
- 浏览器的 `EventSource` 断线后会自动重连并带上 `Last-Event-ID`，不需要手动处理。
- 收到 `run.finished` 后主动 `close()`，否则浏览器会一直重连。

### 2.4 状态：一个 reducer

```ts
// web/src/state/reducer.ts
reduce(state: ViewState, event: RunEvent): ViewState
```

`ViewState` 至少包含：

| 字段 | 来自哪些事件 | 用在哪里 |
|---|---|---|
| 运行信息、当前阶段、计时 | `run.started`、`stage.changed`、`run.finished` | 顶栏 |
| 快照（环号、缺失项） | `snapshot.created` | 左侧信息、开场说明 |
| 每个 Agent 的状态、最新一行思考、token | `agent.status`、`agent.delta`、`usage.updated` | 画布节点 |
| 每个 Agent 的完整思考和工具调用 | `agent.delta`、`tool.started`、`tool.finished` | 节点详情抽屉 |
| 连线：两两之间的消息数、最近一条消息 | `peer.message` | 画布连线生长、气泡 |
| 协作板：判断、修正历史、挂在下面的反应 | `finding.posted`、`finding.revised`、`peer.message`（带 `findingId` 的） | 右栏协作板 |
| 现场提问（待回答 / 已回答） | `human.asked`、`human.answered` | 现场回答卡片、"现场"节点 |
| 会商 | `session.opened`、`session.closed` | 画布上的会商标记 |
| 结论、会签、审核 | `conclusion.drafted`、`signoff.submitted`、`review.decided` | 共识区、印章、第二屏 |
| 协作计数 | `collab.stats` | 顶栏计数器 |

reducer 必须是纯函数：快进回放（设计文档高光 ⑥）就是把同一份事件列表加速重新喂一遍。

## 3. B 后端

### 3.1 目标

一个稳定的运行服务：管理运行生命周期，把事件可靠地推给前端（断线能补发），实现协作中枢，并支持回放模式。

### 3.2 技术栈

Node 22 + TypeScript，用 `tsx` 运行。路由建议用 Hono（`@hono/node-server`），自带 SSE 支持；也可以用原生 `node:http`，只要对外行为符合 `api.ts`。

### 3.3 模块

| 模块 | 职责 | 要点 |
|---|---|---|
| `bus/EventBus` | 每个运行一份事件日志 | 分配 `seq`（从 1 开始连续）和 `ts`；`agent.delta` 按 Agent + kind 每 50 ms 合并；写 `server/runs/<runId>.jsonl`；支持订阅和"从某个 seq 之后补发" |
| `collab/Hub` | 实现 `CollabHub` 接口 | 编号规则 E/H/F/M/Q/S 各自从 1 递增；每个方法发出的事件见接口注释；统计规则见 3.4 |
| `run/RunManager` | 运行生命周期 | 同一时间只允许一个运行（否则 409）；发 `run.started`、`snapshot.created`；调用 C 的编排；编排结束后切到 approval 并等待审核；审核后切到 closed，发 `run.finished`；编排抛错时发 `run.finished(failed)` |
| `run/replay` | 回放模式 | 读 `web/dev/sample-run.jsonl`，按原始时间间隔（除以倍速）重新发出，`runId` 和 `seq` 换成本次运行的；遇到 `human.asked` 时**暂停，等待 `/answer`**；到 approval 阶段时**等待 `/review`**，这样 A 可以在回放模式下调现场回答和审核 |
| `http/routes` | REST + SSE | 严格按 `api.ts`：路径、状态码、`{ error }` 错误格式、SSE 帧格式、15 秒心跳、`Last-Event-ID` 和 `?after=` 两种补发方式 |
| `health` | 预检 | 调一次模型（一句话、不带工具），返回首 token 延迟；失败返回 503 |

### 3.4 CollabHub 统计规则

前端顶栏直接显示这些数字，所以规则要固定：

| 字段 | 规则 |
|---|---|
| `peerMessages` | `send()` 时 `from` 和 `to` 都是专业 Agent（地质、掘进、刀盘、渣土）的消息条数 |
| `asks` / `challenges` / `endorses` | `send()` 时 kind 分别为 ask / challenge / endorse 的条数 |
| `revisions` | `reviseFinding()` 次数 |
| `crossCitations` | `send()` 的 `refs`、`postFinding()` 的 `evidence`、`reviseFinding()` 的 `cites` 中，属于其他 Agent（含现场）的编号个数 |
| `humanAsks` | `askHuman()` 次数 |
| `signoffs` | `signOff()` 次数 |

### 3.5 不依赖 C 的自测

C 的编排接入之前，B 写一个不调模型的假编排 `scripts/fake-orchestration.ts`，实现 `RunOrchestration`：按顺序切阶段、发几条判断、一次质疑、一次修正、一次问现场、起草结论、会签。用它跑通 RunManager 和 Hub，并用 `validateRun()` 校验产出的事件流。

### 3.7 自测命令（写成脚本）

```bash
# 开一个回放运行，倍速 10
curl -s -XPOST localhost:8787/api/runs -H 'content-type: application/json' -d '{"mode":"replay","speed":10}'
# → {"runId":"..."}

# 订阅事件流
curl -N localhost:8787/api/runs/<runId>/events

# 断线补发：只要 seq > 100 的
curl -N 'localhost:8787/api/runs/<runId>/events?after=100'

# 回答现场提问、审核
curl -XPOST localhost:8787/api/runs/<runId>/answer -H 'content-type: application/json' -d '{"questionId":"Q1","text":"有，出土偏干"}'
curl -XPOST localhost:8787/api/runs/<runId>/review -H 'content-type: application/json' -d '{"version":1,"decision":"approve"}'
```

另外写一个 `scripts/check-sse.ts`：开一个回放运行，用 SSE 收完全部事件，交给 `validateRun()` 校验。联调 1 之前必须通过。

## 4. C Agent

### 4.1 目标

把 `server/spike/debate.ts` 变成正式的编排模块，实现 `server/src/contract.ts` 中的 `RunOrchestration`，并让协作指标和结论正确率稳定达到设计文档第 8 节的标准。

### 4.2 从原型拆分

| 原型里的部分 | 拆到哪里 | 改动 |
|---|---|---|
| `systemPrompt`、`ROLE`、各阶段提示词 | `agents/prompts.ts` | 原样迁移，之后在这里调 |
| `bridge()` | `agents/bridge.ts` | 改为调用 `ctx.emit`；不再自己合并 delta（交给 B） |
| `DOMAIN` 数据工具 | `tools/domain.ts` | 证据改为 `hub.addEvidence()` 登记；数据改为从 `ctx.data.ringRange()` 取 |
| `collabTools()` | `tools/collab.ts` | 本地的 `findings`、`reactions`、`stats`、`send` 全部换成 `hub` 的方法；`checkRefs` 改用 `hub.missingRefs()` |
| `answerAs()` 应答分身 | `orchestration/answerer.ts` | 不变 |
| `steerOthers()` 广播 | `orchestration/delivery.ts` | 改为订阅 `hub.onDeliver`：对方正在运行就 `steer()`，否则 `hub.defer()`；背靠背阶段不投递 |

| 模拟现场回答（话术卡匹配） | 删除 | 改为 `await hub.askHuman(q, 90_000)` |

### 4.3 原型里还没有、需要补上的

| 项 | 要求（设计文档出处） |
|---|---|
| 交叉互评的硬性要求 | 每个 Agent 至少对 2 位同伴表态；不足时用 `steer()` 提醒一次（2.3 节） |
| 预算 | 单个 Agent 每阶段 6 轮或 60 秒；`ask_peer` 单次 30 秒；整轮 5 分钟（5.8 节）。超时后标记并继续，不能卡住流程 |
| 中止 | `ctx.signal` 触发时，对所有 Agent（含应答分身）调用 `abort()` |
| 现场提问的 gap 校验 | 必须从 `ctx.data.missing` 中选（工具参数直接用枚举） |
| 会签保留意见 | `agree: false` 或带 note 时，写入结论的少数意见 |
| 批量测试脚本 | `scripts/batch-run.ts`：连跑 N 次，输出每次的协作统计、结论是否正确、用时；与第 8 节标准逐项对比 |
| 已知小问题 | 录制中模型偶尔会调用不存在的工具 `brief`（把参数名当成了工具名），pi 会返回错误让它重试，不影响流程；可以考虑把参数名改成 `short` 之类不像动作的名字后观察是否消失 |

## 6. 联调出问题时谁先查

| 现象 | 先查的人 | 方法 |
|---|---|---|
| 页面收不到事件 | B | `curl -N` 直接连 SSE，看有没有数据 |
| 事件收到了但画面不对 | 先跑 `validateRun()` | 校验不通过找 B（或 C，看是哪类事件，见 `contract.ts` 的分工）；校验通过找 A |
| `agent.*`、`tool.*` 类事件缺失或错误 | C | 查事件桥接 |
| 协作类事件（判断、消息、统计）错误 | B | 查 Hub |
| 协作行为不够（质疑少、不改口） | C | 看批量统计，调提示词 |
| 结论错误 | C | 对照设计文档第 5 节的参考答案 |
| 刷新后画面错乱 | A 和 B 一起 | 先确认补发的事件 `seq` 连续、无重复，再查 reducer 的去重 |
